## 真实服务故障与恢复

证据：`test-results/live-integration.json`。

- 独立 HTTP 目录服务延迟 12 秒，调用在 **7.437 秒**结束并报超时；关闭故障设置后恢复读取。
- 独立计费 HTTP 服务返回 503，发送任务保持待重试状态。
- 实际停止并重新创建工作进程，过期租约任务恢复发送。
- 已送达的正式账单再次经 HTTP 重发 3 次，接收方账单数量保持不变。
- 单元/集成测试额外验证 SQL 目录适配器的 7.5 秒总期限、有效缓存/过期缓存，以及失败退避达到上限后仍继续重试。

## 500 / 2000 用户压测

硬件：AMD Ryzen 7 5700U（8 核、16 逻辑处理器），可用物理内存总量 **13.85 GiB**；Windows 11 build 26200；Python **3.12.0**；MySQL **8.0.43**，项目私有实例 3307。压测客户端、API 服务和 MySQL 共用这一台电脑，运行时仍有其他日常应用占用内存。

最终配置：每个 API 服务 **2 个工作进程**，每进程固定 **8 个 MySQL 连接**。2000 用户分配给 4 个本机服务端口，每个服务 500 用户，共享同一个 MySQL 数据库。目录的固定学期结构使用有时限缓存，剩余名额、任课教授、教学班状态和用户成绩仍从数据库实时读取。

场景：为每个用户预建独立账号和会话，用 **10 秒**逐步进入工作台，再同步发起无思考时间的操作；每人连续 2 轮，每轮包含课程目录查询、本人课表查询、保存草稿。使用 aiohttp 客户端。统计不包含登录密码哈希、首次建立连接阶段或计费批处理。

| 用户数 | 服务数 × 工作进程 | 测量操作数 | 成功率 | P80 | P95 | 目录最慢响应 | 120 秒内成功比例 |
|---|---|---:|---:|---:|---:|---:|---:|
| 500 | 1 × 2 | 3000 | **100%** | **3.905 秒** | 4.496 秒 | **4.887 秒** | **100%** |
| 2000 | 4 × 2 | 12000 | **100%** | **6.508 秒** | 7.611 秒 | **9.247 秒** | **100%** |

对应原始文件：`test-results/load-500.json`、`test-results/load-2000.json`。在这一明确的已登录工作台场景中，80% 在两分钟内完成、目录响应不超过 10 秒的目标均达到。

**额外极端场景未通过：**直接在同一时刻建立 2000 个全新 TCP 连接并请求，曾出现目录响应 10.78～11.87 秒；另一次出现 217 次超时。该场景的失败记录保留在 `load-2000-cold-connection-spike.json` 及其他带说明后缀的 JSON 中，没有当作通过结果。登录洪峰、瞬间新连接洪峰、跨机器部署和所有类型事务的组合压力仍需要另行验证和容量调优。当前结果不能解释成任意流量形态均满足延迟上限。

调试期间保留了单工作进程、旧连接池、HTTPX 压测客户端和查询优化前的原始记录。修复包括：缓存刷新合并、固定连接池、复用数据库 TLS 上下文、只缓存固定目录结构、减少重复 SQL 和通用 JSON 编码开销。切换压测客户端以及连接预热改变了测试方法，最终结果的适用范围按上面的场景定义判断，不把不同方法的数据当成严格的性能提升比例。
